# v3.4.0

Compared with v3.3.7 (`45da127b`), this release adds synchronous evaluation of
asynchronous module graphs, improves module semantics, and updates the build and
release tooling. The CommonJS factory API remains
`require("esm-sync")(module, options)`.

## Module loading

- Load fully evaluated exports from modules and dependencies containing top-level
  `await`, including asynchronous cycles and dynamic imports. Namespace identity,
  live bindings, and original rejection values are preserved.
- Support module-body `for await...of`, `using`, and `await using`, including
  iterator closing and resource disposal on abrupt exits.
- Add import attributes, text imports, deferred imports, and string-named module
  exports. Improve binding identity and ambiguous star re-export handling.
- Fix lexical `require` declarations, including the
  `const require = createRequire(import.meta.url)` pattern.
- Improve package export-pattern substitution, URL query/fragment resolution, and
  validation of disk compilation-cache metadata.

## Jest and compatibility

- Preserve CommonJS constructor identity across dependencies loaded through
  `esm-sync`, fixing affected `instanceof` checks and js-yaml schema construction.
- Reuse CommonJS modules preloaded by Jest and refresh loader-owned CommonJS state
  after `jest.resetModules()`, including retained loader factories.
- Preserve non-enumerable globals and lazy getters when recreating Jest VM
  contexts. This fixes missing `DOMException` errors in dependencies such as
  Undici and `@kubernetes/client-node` on affected Node versions.
- Restore physical `esm.js` and `index.js` compatibility entries and their
  declarations after the move to `dist/`. Package subpaths and direct filesystem
  entry paths remain available, including on Node versions without export maps.
- Keep loader startup compatible with realms that do not expose `globalThis`.

## Optional native bridge and installation

- Ordinary imports and microtask-settled awaits use the JavaScript loader.
  Synchronous top-level awaits that need timers or I/O require a compatible
  native bridge. The bridge targets Node 22 and newer and is specific to the
  operating system, architecture, and Node ABI.
- The install hook first reuses a valid bundled bridge; otherwise it attempts a
  local build using matching Node headers and a C++20 compiler. An unavailable
  compiler does not disable ordinary loading.
- Skipping dependency build scripts leaves matching bundled binaries usable.
  Without a compatible bridge, timer/I/O awaits fail explicitly with
  `ERR_ESM_SYNC_ASYNC_PENDING`. No compiler or download runs during module loading.
- pnpm 12 may reject an unreviewed dependency build. Explicitly allow or deny it
  using `allowBuilds` or the workspace's `permissions` policy. To opt out, set
  `allowBuilds: { esm-sync: false }`.
- Bound synchronous async evaluation with `ESM_SYNC_AWAIT_TIMEOUT_MS` (default
  5,000 ms). Unsafe event-loop re-entry raises `ERR_ESM_SYNC_ASYNC_REENTRANT`.

## Tooling and releases

- Migrate maintained source and tooling to strict TypeScript, with generated
  CommonJS output and public declarations bundled by tsdown.
- Expand native subprocess, Test262, declaration, package, and registry checks.
- Add tested beta and stable release workflows, tarball validation, and trusted
  npm publishing. Fix the beta tarball directory mismatch.

## Compatibility notes and known limitations

- The declared Node engine range remains `>=6` for the ordinary loader. New
  syntax and native-bridge functionality have additional runtime requirements.
- Timer/I/O-backed synchronous awaits are supported on the initial CommonJS
  startup stack. Active callbacks, Promise reactions, and worker contexts have
  re-entry restrictions; see [async module loading](../async-module-loading.md).
- Jest 26's `jest.isolateModules()` does not automatically partition the private
  CommonJS cache used to preserve constructor identity. A retained loader can
  reuse an outer constructor inside an isolated callback; v3.3.7 reevaluated it.
  This remains a known compatibility regression. Use `jest.resetModules()`
  between independent scenarios when fresh state is required. That resets the
  whole Jest registry and does not preserve the outer scope as an isolated
  registry would.
- Direct paths into the private loader bundle are internal; published public
  factory entry points and declarations remain supported.
